## 1. Кратко

| | 0.3 | 1.0.0 |
|---|---|---|
| Список хостов | загружается перед каждым циклом, блокирует пинг | загружается в фоне раз в 5 минут, синхронизируется с внутренним хранилищем |
| Атрибуты хостов | только `ip`, `status`, `target_group` | плюс любые поля с префиксом `_` (`_id`, `_name`, `_location`…) — в репорте, API, метриках |
| `status: null` | превращался в `0` (хост считался упавшим) | статус неизвестен: берётся с прошлого прохода, первый статус уходит в репорт в любом случае |
| Алгоритм | `fast_mode` или процентный режим, по умолчанию процентный | один алгоритм (бывший `fast_mode`) |
| Статус работающего хоста | `100` (`fast_mode`) или процент успешных инспекций | процент полученных пакетов за цикл, `1`–`100` |
| Фиксация падения | по умолчанию после **1** провальной инспекции из 3 | после **10** провальных инспекций подряд |
| Состояние между циклами | нет, всё берётся из списка хостов | внутреннее хранилище: статусы, задержки, потери, окна 1m/5m, история |
| Репорт | `{ip, status, target_group}` | плюс `icmp`, `tcp`, `latency`, `latency_1m`, `latency_5m`, `loss`, атрибуты |
| Когда хост уходит в репорт | статус изменился относительно статуса в списке хостов | статус расходится с известным серверу: изменился за цикл, прошлый репорт не дошёл или в списке хостов другой статус |
| Отключение репортов | нет | `api.report_enabled: false` |
| Реалтайм | нет | хосты «падает» / «поднимается» видны после каждой инспекции |
| Веб-интерфейс | нет (только `/metrics`) | дашборд, REST API, websocket |
| События | нет | websocket и redis pub/sub |
| Метрики хостов | `host`, удалённые хосты оставались навсегда | строятся из текущего состояния, атрибуты, режимы детализации |
| Логгер | `all-ok-radius-server/logger`, числовые уровни | logrus, уровни `debug`/`info`/`warn`/`error`, формат `text`/`json` |
| Отправка ICMP | общий сокет, пауза после каждого пакета | отдельный сокет на writer, общий темп `packets_per_second` |
| Пауза между циклами | `sleep_after_check` после цикла | `sleep_interval` — фиксированный период |

## 2. Совместимость

**Сохранено:**

* **API списка хостов.** Тот же запрос `GET <host_list_url>?ident=<ident>` и тот же ответ `{"data": [...]}`.
  Старый список без атрибутов работает без изменений.
* **API репортов.** Тот же `POST <report_url>?ident=<ident>` с JSON-массивом хостов. Поля `ip`, `status`, `target_group`
  на месте, значения статусов те же (`100`, `0`, `999`). Добавлены новые поля — принимающая сторона должна их игнорировать.
* **Имена системных метрик** с опечаткой `cicles` (`icmp_pinger_sys_cicles_count`, `icmp_pinger_sys_cicles_sec`) —
  чтобы не сломать существующие графики и алерты.
* **Имена основных метрик хостов:** `icmp_pinger_peer_status`, `icmp_pinger_peer_latency_sec`,
  `icmp_pinger_peer_ping_packages`, `icmp_pinger_peer_pong_packages`, `icmp_pinger_peer_cicles`.
* **Переменные окружения** `API_HOST_LIST_URL`, `API_REPORTS_URL`, `API_TIMEOUT`, `PINGER_IDENT`.
* **Формат подстановки** `${VAR:default}` в YAML.

**Изменилось несовместимо:**

* **Структура конфигурационного файла.** Секции `system` и `pinger` расформированы, часть параметров переименована
  или удалена. Старый `pinger.config.yml` не подойдёт — см. [раздел 13](#13-конфигурация-соответствие-параметров).
* **Переменные окружения** `SLEEP_AFTER_CHECK` и `LOG_LEVEL_INT` больше не используются. Числовые уровни логов
  не поддерживаются: значение вроде `LOG_LEVEL=6` остановит пингер при старте.
* **`target_group` в репорте** раньше передавался всегда (пустой строкой, если группы нет), теперь — только если задан.
* **Смысл процента в статусе другой.** В 0.3 без `fast_mode` статус был процентом успешных инспекций, с `fast_mode` — всегда `100`.
  Теперь у работающего хоста статус — процент полученных пакетов за цикл (`1`–`100`). Условие «`status > 0` — up» сохраняется.
* **Репорт уходит при любом изменении статуса**, в том числе при изменении процента (`100` → `75`), поэтому хосты с потерями
  попадают в репорт чаще, чем в 0.3.
* **Метрики:** удалена `icmp_pinger_peer_inspections_count`; у метрик хостов добавлен лейбл `target_group`;
  `icmp_pinger_peer_status` теперь — текущий статус по результатам проверки, а не статус из списка хостов
  (см. [раздел 10](#10-метрики-prometheus)).
* **Порт метрик.** Отдельного `prometheus.port` нет: метрики отдаются веб-сервером на `/metrics`
  (`web.listen`, по умолчанию `:2112` — тот же порт, что был у метрик в 0.3).

## 3. Принцип работы: было и стало

### 3.1. Цикл

**0.3:**

1. Загрузить список хостов (при ошибке — повтор через 10 с).
2. Пропинговать все хосты.
3. Отправить репорт по хостам, у которых статус отличается от статуса в списке (при ошибке — пауза 10 с и новый цикл).
4. Подождать `sleep_after_check` (10 с) и вернуться к пункту 1.

**1.0.0:**

* Список хостов загружается в фоне раз в `api.host_list_refresh_interval` (5 мин) и синхронизируется
  с внутренним хранилищем. На ход цикла загрузка не влияет. Первая загрузка при старте — блокирующая.
* Цикл запускается раз в `sleep_interval` (30 с), отсчёт от начала цикла. Если цикл длится дольше —
  следующий начинается сразу, в лог пишется предупреждение.
* Цикл: взять хосты из хранилища → ICMP-инспекции → TCP-проверка падающих → обновить хранилище →
  репорт по хостам, чей статус расходится с известным серверу → события в redis и websocket.
* Если репорт не отправился, хосты попадут в репорт следующего цикла: отправленным статус считается
  только после HTTP 200. Подробнее — в [разделе 6](#6-репорты).

### 3.2. Инспекции

**0.3** — два режима, по умолчанию `fast_mode: no`:

* без `fast_mode` все хосты проходят все инспекции, итоговый статус — процент успешных инспекций
  (при `number_of_inspection: 3` получались `100`, `66`, `33`), хост «падал» после
  `must_inspections_failed_for_down: 1` провальной инспекции из трёх;
* с `fast_mode` хост, подтвердивший статус, выбывал из цикла.

**1.0.0** — один алгоритм (бывший `fast_mode`):

* Инспекция: каждому хосту отправляется `icmp.packets` (4) пакетов **по кругу** — сначала 1-й пакет всем хостам,
  затем 2-й и т. д., в случайном порядке хостов, с общим темпом `icmp.packets_per_second` (15 000).
  Хост ответил, если пришёл хотя бы один ответ.
* После отправки — ожидание ответов `icmp.response_timeout` (2 с).
* Хост, подтвердивший свой статус (up и ответил, down и не ответил), выбывает из цикла.
  Остальные проверяются снова через `icmp.inspection_interval` (3 с), максимум `icmp.inspections` (10) инспекций:
  * **up → down** — `icmp.failed_for_down` (10) провальных инспекций подряд, затем TCP-проверка;
  * **down → up** — `icmp.success_for_up` (2) успешных инспекций подряд.
* Хост, по которому решение принято, сразу выбывает — лишних инспекций не делается.

### 3.3. Статусы

| Статус | Значение |
|---|---|
| `1`–`100` | up — процент полученных ICMP-пакетов за цикл. `100` — ответил на все пакеты, даже если проверялся одну инспекцию; не меньше `1`, чтобы работающий хост всегда был `> 0` |
| `0` | down — не ответил в `failed_for_down` инспекциях подряд (и не прошёл TCP-проверку, если она включена) |
| `999` | не отвечает по ICMP, но принимает TCP-подключение на один из `tcp.ports` |
| `null` | статус неизвестен (только во входящем списке хостов и в API до первой проверки) |

Примеры: ответил на 4 пакета из 4 в первой инспекции и выбыл — `100`; пропустил 2 инспекции и вернулся
(отправлено 12, получено 4) — `33`; не ответил в 10 инспекциях подряд — `0`. Хост, который был down и ответил
меньше чем в `success_for_up` инспекциях подряд, остаётся `0`.

Хост с неизвестным статусом проверяется как up: если ответил — процент полученных пакетов, если не ответил
в `failed_for_down` инспекциях подряд — `0`. Поэтому первый цикл после старта (когда все статусы `null`) идёт примерно столько же,
сколько обычный.

### 3.4. Известный статус хоста

В 0.3 статус «до проверки» всегда брался из списка хостов. В 1.0.0 — по приоритету:

1. статус прошлого прохода (фактическое состояние пингера);
2. если состояния ещё нет (хост новый или пингер перезапущен) — то, что известно серверу:
   последний отправленный статус или статус из списка хостов (если `api.ignore_host_list_statuses: false`);
3. `null`.

Проверка идёт относительно фактического состояния, а репорт — относительно того, что известно серверу
(см. [раздел 6](#6-репорты)). Поэтому, если репорт не дошёл, упавший хост не проверяется заново 10 инспекций
и не даёт ложных событий `falling`, но остаётся в очереди на отправку.

## 4. Исправленные ошибки версии 0.3

| Ошибка в 0.3 | Последствие | Как сейчас |
|---|---|---|
| Учитывался любой ICMP echo reply без проверки ID | ответы другим процессам на сервере (другой пингер, `ping`) засчитывались хостам | у пакетов случайный ID экземпляра, чужие ответы отбрасываются |
| Не было дедупликации ответов | дублирующиеся ответы засчитывались как отдельные пакеты | ответы учитываются по номеру пакета, дубли отбрасываются |
| Ответ не привязывался к инспекции и циклу | опоздавший ответ из прошлой инспекции засчитывался в текущую | в пакете номер цикла и инспекции; ответ засчитывается только своей инспекции |
| Результат TCP-проверки писался в тот же кэш, что ICMP-ответы | опоздавший ICMP-ответ во время TCP-проверки мог дать хосту статус `999` без TCP-подключения | результат TCP хранится отдельно для каждого хоста |
| TCP-проверка ждала фиксированное время (`ports × connect_timeout`) после постановки в очередь | при большом количестве падающих хостов часть проверок не успевала завершиться | цикл ждёт завершения всех TCP-проверок |
| Задержка = время от последней отправки до любого ответа, перезаписывалась каждым пакетом | `icmp_pinger_peer_latency_sec` была приблизительной | время отправки в самом пакете, честный RTT каждого ответа; min/max/avg за проход и окна 1m/5m |
| `status: null` в списке превращался в `0` | неизвестный хост считался упавшим | `null` — неизвестный статус |
| Строковый статус (`"100"`) ломал разбор всего списка | пингер не получал список хостов | принимается число или строка |
| Не проверялся HTTP-статус ответа API списка хостов | ответ с ошибкой мог разобраться как пустой список хостов | ошибка, повтор, старый список остаётся в работе |
| `?ident=` дописывался к URL строкой | URL с параметрами ломался | параметр добавляется к query корректно |
| Метрики хостов создавались через глобальные gauge | хосты, удалённые из списка, оставались в метриках навсегда | метрики строятся из текущего состояния на каждый scrape |
| `icmp_pinger_peer_status` выставлялся из статуса списка до проверки | метрика показывала то, что прислал сервер, а не результат проверки | текущий статус по результату |
| Буфер приёма сокета по умолчанию (~208 КБ) | на 50к+ хостов ядро теряло ответы — ложные падения | буфер 32 МБ (`SO_RCVBUFFORCE`) |
| Отправка через один общий сокет с паузой после каждого пакета | отправка упиралась примерно в 11к пакетов/с, темп зависел от точности таймера | отдельный сокет на writer, пауза «пачками» от 1 мс, точный общий темп |
| По умолчанию down после 1 провальной инспекции из 3 | флапы при кратковременных потерях | down после 10 провальных инспекций подряд |

## 5. Список хостов

```json
{"data": [
  {"ip": "10.0.0.1", "status": 100, "target_group": "core", "_id": 15, "_name": "sw-1", "_location": "Kyiv"},
  {"ip": "10.0.0.2", "status": null}
]}
```

* **Атрибуты** — любые поля с префиксом `_`. Передаются как есть в репорт, API, события, а в метрики — лейблами
  без префикса (`_location` → `location`). Числа сохраняются числами.
* **`status`** — число, строка или `null`.
* **`target_group`** — необязательный.
* **Фоновая синхронизация:** новые хосты добавляются, у существующих обновляются атрибуты и группа
  (статус и история сохраняются), отсутствующие удаляются. Результат проверки хоста, удалённого во время цикла,
  отбрасывается. При ошибке загрузки работа продолжается по старому списку, повтор через 30 с.
* **`api.ignore_host_list_statuses: true`** — статусы из списка игнорируются (как `null`).
* Время загрузки списка 55к хостов — 5–7 с.

## 6. Репорты

`POST <api.report_url>?ident=<ident>`, тело — массив хостов, **у которых за цикл изменился статус**:

```json
[
  {
    "ip": "10.33.123.121", "status": 0, "icmp": false, "tcp": false,
    "latency": null,
    "latency_1m": {"min": 1.92, "max": 12.796, "avg": 4.121},
    "latency_5m": {"min": 1.92, "max": 12.796, "avg": 4.121},
    "loss": {"transmitted": 40, "received": 0, "loss": 100},
    "_id": 17126688, "_location": "Киев, ул. Героев Днепра улица, h.19(1)", "_model": "DGS-3000-28XS", "_rank": 3
  }
]
```

| Поле | Описание |
|---|---|
| `ip` | как в 0.3 |
| `status` | `1`–`100` (процент полученных пакетов), `0`, `999` — см. [раздел 3.3](#33-статусы) |
| `target_group` | только если задан в списке хостов |
| `icmp` | были ли ответы по ICMP в этом цикле |
| `tcp` | результат TCP-проверки; `null`, если TCP выключен или проверка не выполнялась |
| `latency` | min / max / avg RTT за текущий цикл, мс; `null`, если ответов не было |
| `latency_1m`, `latency_5m` | то же по скользящим окнам |
| `loss` | отправлено / получено / процент потерь за цикл |
| `_…` | атрибуты из списка хостов |

В репорт попадают хосты, чей статус у пингера расходится с тем, что известно серверу. Если таких нет, запрос не уходит.
Расхождение возникает в трёх случаях:
1. статус изменился в этом цикле;
2. прошлый репорт не дошёл (отправленным статус считается только после HTTP 200) — хост уходит в следующем цикле;
3. в списке хостов, загруженном после последней отправки, у хоста другой статус (например, в списке `0`, а хост работает).
   `status: null` в списке означает, что сервер статус не сообщает, — такие хосты расхождения не дают.

Что известно серверу — более свежий из двух статусов: последний отправленный или статус из списка хостов.
Хосты, ждущие отправки, видны в API (`report_pending: true`), на дашборде (фильтр «Ждут репорта»)
и в метрике `icmp_pinger_sys_report_pending_hosts`.

* Изменением считается любое изменение статуса, в том числе процента у работающего хоста.
* Хосты со статусом `null` в списке попадают в репорт после первой проверки в любом случае,
  в том числе после каждого рестарта пингера (отправленные статусы хранятся только в памяти).
* Если сервер отвечает 200, но не обновляет статус у себя, хост будет уходить в репорт после каждой загрузки
  списка хостов (раз в `api.host_list_refresh_interval`).
* В redis-канал репортов уходят только изменения за цикл, без повторов неотправленных.
* `api.report_enabled: false` (или пустой `report_url`) — репорты не отправляются.
* Отдельного «старого» формата нет: поля `ip` и `status` есть в любом случае.

## 7. Реалтайм-состояния: «падает» и «поднимается»

Статус фиксируется (и уходит в репорт) только после всех инспекций цикла. Внутри цикла после каждой инспекции видно:

* **falling** — хост со статусом up не ответил в `realtime.falling_after_inspections` (3) инспекциях;
* **rising** — хост со статусом down ответил в `realtime.rising_after_inspections` (1) инспекции.

В конце цикла переход закрывается одним из событий: `status_changed` (хост упал или поднялся) или
`falling_cancelled` / `rising_cancelled` (хост остался up / down). Если хост вернулся с потерями, приходят оба:
`falling_cancelled` и `status_changed` с новым процентом (`100` → `33`).

Где видно: поля `state` и `pending` в `/api/v1/hosts`, фильтр `?state=falling,rising`, прогресс цикла
в `/api/v1/summary`, сообщения `inspection` в websocket, события в redis, блок «Сейчас в переходе» на дашборде.

Порог 3 выбран по замерам: при пороге 2 половина переходов отменялась — это хосты с потерями,
пропустившие ровно 2 инспекции.

## 8. Веб-сервер, API, websocket и дашборд

В 0.3 был только `/metrics`. В 1.0.0 веб-сервер (`web.listen`, по умолчанию `:2112`):

| Путь | Описание |
|---|---|
| `/` | дашборд |
| `GET /api/v1/hosts` | все хосты; фильтры `status=up\|down\|unknown`, `state=up,down,unknown,falling,rising`, `target_group=`, `ip=a,b`, `q=` |
| `GET /api/v1/hosts/{ip}` | один хост |
| `GET /api/v1/summary` | сводка: хосты по состояниям, группы, последний цикл, прогресс текущего цикла, список хостов |
| `GET /api/v1/events?types=…&limit=…` | последние события (до 2000), новые первыми |
| `GET /api/v1/ws` | websocket |
| `GET /api/v1/config` | конфигурация без секретов (пароли и токены в URL замаскированы) |
| `GET /health` | проверка доступности |
| `/metrics` | метрики Prometheus |
| `/debug/pprof/` | профилирование, только при `web.pprof: true` |

Ответы `/api/v1/hosts`, `/api/v1/summary`, `/api/v1/events` сжимаются gzip (55к хостов: 42 МБ → 2,9 МБ).

### Объект хоста в API

Объект репорта плюс служебные поля: `state`, `pending`, `list_status` (статус из списка), `report_pending` (ждёт отправки в репорте), `reported_status`
(последний отправленный), `loss_1m`, `loss_5m`, `checked_at`, `changed_at`, `reported_at`, `cycles`, `flaps`,
`flapped_at`, `error`.

### Websocket `/api/v1/ws`

* События хостов — в том же формате, что в redis.
* `{"type":"inspection","progress":{…},"pending":[…]}` — после каждой инспекции, все хосты в переходе
  с текущими счётчиками.
* `{"type":"cycle","cycle":{…}}` — цикл завершён.
* `{"type":"ping"}` — раз в 30 с.
* Фильтры: `?types=falling,rising,cycle`, `?ip=10.0.0.1,10.0.0.2`.
* Медленный клиент отключается и не тормозит остальных.

### Дашборд

* **Сводка:** карточки (всего, up, down, падают, поднимаются, unknown, только TCP, с потерями, средний RTT,
  длительность цикла, изменения/репорт, циклы), прогресс текущего цикла, состояние websocket.
* **«Сейчас в переходе»:** падающие и поднимающиеся хосты с прогрессом `n/10`, обновляются после каждой инспекции.
* **Лог падений и поднятий:** последние смены статуса, по желанию — с переходами; заполнен сразу при открытии.
* **«Хосты»:** таблица с колонками атрибутов, сортировка, поиск, фильтры по статусу; строки обновляются из событий.
* **«Группы»:** группировка по `target_group`, состоянию или любому атрибуту; счётчики, доступность, средний RTT;
  раскрытие группы, переход в список хостов с фильтром.
* **«События»:** живая лента с фильтрами и паузой.
* **«Настройки»:** последний цикл, загрузка списка хостов, конфигурация.
* Атрибуты подписаны без `_`. Настройки (группировка, сортировки, раскрытые группы, фильтры, вкладка)
  сохраняются в localStorage браузера.
* Список хостов загружается при подключении и после каждого цикла, всё остальное приходит по websocket.

## 9. Redis

В 0.3 не было. В 1.0.0 — публикация через pub/sub (`PUBLISH <канал> <json>`), по умолчанию выключена.

* `redis.events_key` (`pinger:events`) — события:

  | Тип | Когда |
  |---|---|
  | `falling` / `rising` | хост начал падать / подниматься (один раз за цикл) |
  | `status_changed` | статус зафиксирован и изменился, в том числе процент (`100` → `75`) |
  | `falling_cancelled` / `rising_cancelled` | переход не подтвердился |
  | `host_added` / `host_removed` | хост добавлен в список / удалён из него (не при первой загрузке) |

  ```json
  {"ident":"PINGER-UKRAINE","type":"status_changed","ip":"10.95.125.108","time":"2026-11-12T10:01:25.72+02:00",
   "status":0,"prev_status":100,"state":"down","host":{…объект репорта…}}
  ```

* `redis.reports_key` (`pinger:reports`) — репорты пачками по 1000:
  `{"type":"report","ident":…,"time":…,"count":…,"items":[…]}`.
* Отправка асинхронная, через очередь (`queue_size`) пачками до 500 в одном pipeline, 3 попытки.
  Пинг не блокируется; при переполнении очереди сообщения отбрасываются (видно в метрике).

## 12. Производительность

Замеры на рабочем списке — 55 382 хоста.

* Сеть держит 20–30 тыс. пакетов/с без роста потерь; при 50 тыс./с потери ~12%, при 95 тыс./с — ~55%.
* В 0.3 отправка через общий сокет упиралась примерно в 11 тыс. пакетов/с. Теперь у каждого writer'а свой сокет,
  их число вычисляется из `packets_per_second` (~8 тыс. пакетов/с на writer).
* С буфером приёма по умолчанию ядро теряло ответы (сотни тысяч за цикл); буфер 32 МБ эту проблему убрал.
* Настройки по умолчанию (10 инспекций, 4 пакета, 15 тыс. пакетов/с, ожидание 2 с, пауза 3 с):

  | | Время |
  |---|---|
  | Первая инспекция (все хосты) | ~17,5 с |
  | Повторная инспекция (сотни хостов) | ~2,1 с |
  | Первый цикл после старта | ~81 с |
  | Обычный цикл | ~63 с |
  | Фиксация падения | ~1 мин после первого пропуска |

* Смен статуса за цикл в спокойное время — 7–14, все подтверждаются независимым `ping`.

## 14. Переход с 0.3 на 1.0.0

1. **Конфиг.** Взять новый `pinger.config.yml`, перенести свои значения по таблице из раздела 13.
   В Docker-образе уже лежит новый конфиг — достаточно переменных окружения.
2. **Переменные окружения:**
   * `SLEEP_AFTER_CHECK` → `SLEEP_INTERVAL`. Смысл другой: это период цикла, а не пауза.
     Цикл на 55к хостов идёт ~63 с, поэтому `sleep_interval: 60s` — разумное значение;
     при 30 с циклы идут подряд и в лог пишется предупреждение.
   * `LOG_LEVEL_INT` → `LOG_LEVEL` со значением `debug`/`info`/`warn`/`error`.
3. **Сервер, принимающий репорты**, должен игнорировать незнакомые поля и отсутствие `target_group`.
4. **Список хостов.** Менять не обязательно. Если нужны атрибуты в репорте, метриках и дашборде — добавить поля с `_`.
   Если сервер не знает статусов — можно отдавать `null`.
5. **Prometheus:**
   * запросы с `icmp_pinger_peer_inspections_count` — убрать;
   * агрегации без `by` / `without` по `icmp_pinger_peer_*` не изменятся, но у рядов появился лейбл `target_group`;
   * графики по `icmp_pinger_peer_status` теперь показывают результат проверки;
   * добавить алерты из раздела 10.
6. **Порт 2112** теперь отдаёт ещё дашборд и API. Если пингер доступен снаружи — закрыть порт фаерволом
   или вынести за прокси с авторизацией (см. раздел 16).
7. **Redis** — по желанию: `REDIS_ENABLED=true`, `REDIS_ADDR`, при необходимости `REDIS_EVENTS_KEY` / `REDIS_REPORTS_KEY`.
8. **Права.** Как и раньше, нужны raw-сокеты (root или `CAP_NET_RAW`). Для буфера приёма 32 МБ без ограничения
   `net.core.rmem_max` нужен `CAP_NET_ADMIN` (`SO_RCVBUFFORCE`); без него буфер ограничен системной настройкой,
   в лог пишется предупреждение.

## 16. Ограничения и открытые вопросы

* **Нет авторизации** на дашборде, API и `/metrics` — в API видны все хосты с атрибутами.
  Публиковать порт наружу без фаервола или прокси не стоит.
* **Redis pub/sub не хранит сообщения:** если подписчика нет, событие теряется.
  Восстановить пропущенное можно через `/api/v1/hosts` или `/api/v1/events` (последние 2000 событий).
* **Состояние хранится в памяти.** После рестарта история (окна 1m/5m, флапы) начинается заново;
  статусы берутся из списка хостов.
* **IPv6** поддерживается кодом, но на рабочем списке не проверялся.
* **`sleep_interval` по умолчанию 30 с** меньше длительности цикла на 55к хостов — циклы идут подряд.
* **`status_changed` не отправляется** для первого статуса хоста без известного прежнего статуса
  (`prev_status: null`) — такой хост попадает только в репорт.
